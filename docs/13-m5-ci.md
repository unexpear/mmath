## The matrix paid off immediately

First GCC run caught a real latent bug invisible on MSVC: argument
evaluation order is unspecified, and three factories read a vector's size
in the same argument list that moves from it (`JustIntonation::create`,
`CentsTuning` ctor, `HarmonicSeries::create`). MSVC happened to evaluate
size-first; GCC evaluated move-first (`"just[0 ratios]"`). Fixed by
counting before moving; formula-string pins added for all three so the
class stays caught. This is the exact portability drift ADR-015 predicted.

## Honest remainder

- **The original claim here was wrong in one detail**: it said the workflow
  "mirrors exactly what ran locally". The build, test and sanitizer gates
  did, but the toolchain-printing step had never run anywhere, and it was
  the step that failed. Hosted execution is now proven; the correction is
  kept rather than erased.
- **Sanitizer reports are only fully checked locally.** The hosted
  sanitize job fails on ASan aborts via ctest, but UBSan prints a report
  and continues by default, so a passing hosted job does not by itself prove
  zero UBSan reports. The zero-report claim rests on the local direct runs
  (tests plus every example) that grep sanitizer output. Making the hosted
  job fail on any UBSan report (`UBSAN_OPTIONS=halt_on_error=1`) and
  running the examples there is follow-up work.
- No second-round portability findings: all compilers agree on every test,
  including the move-order regression pins.
- `build*` dirs are local scratch (gitignored), not committed.
