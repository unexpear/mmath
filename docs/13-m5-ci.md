## The matrix paid off immediately

First GCC run caught a real latent bug invisible on MSVC: argument
evaluation order is unspecified, and three factories read a vector's size
in the same argument list that moves from it (`JustIntonation::create`,
`CentsTuning` ctor, `HarmonicSeries::create`). MSVC happened to evaluate
size-first; GCC evaluated move-first (`"just[0 ratios]"`). Fixed by
counting before moving; formula-string pins added for all three so the
class stays caught. This is the exact portability drift ADR-015 predicted.

## Honest remainder

- **The original claim here was wrong in one detail**: it said the workflow
  "mirrors exactly what ran locally". The build, test and sanitizer gates
  did, but the toolchain-printing step had never run anywhere, and it was
  the step that failed. Hosted execution is now proven; the correction is
  kept rather than erased.
- **Sanitizer gap: found, then closed (commit `c6a364b`).** UBSan prints a
  report and continues by default. A deliberate signed-overflow probe built
  with the original flags printed `runtime error` and **exited 0**, so a
  green sanitize job did not prove zero UBSan reports. Findings are now
  fatal in two independent ways, with a third check:
  1. `-fno-sanitize-recover=all` added to the `MMATHEN_SANITIZE` flags in
     CMake (applies locally and in CI; present in all 92 sanitized compile
     lines).
  2. `UBSAN_OPTIONS=halt_on_error=1` (and `ASAN_OPTIONS=detect_leaks=1`) on
     the hosted sanitize job.
  3. A new step runs every example named in CMakeLists' `foreach(example
     ...)` list. It fails on a missing binary, a non-zero exit, or any
     sanitizer text in the output.

  **The gate was shown to fail before it was trusted to pass.** The step
  script, extracted verbatim from the workflow, was run locally. It passed
  on the real build (215/215 tests, 16/16 examples clean) and failed, as it
  should, in four negative cases:
  - an example replaced by the UB probe, with `halt_on_error=1`
  - the same probe with no environment setting (the output scan alone
    caught it)
  - the probe built with `-fno-sanitize-recover=all`
  - a missing example
  (A first negative run was discarded: a WSL restart had cleared the probe
  binaries, so those cases failed for the wrong reason.)

  **Hosted run 35131747143 (commit `c6a364b`): all 7 jobs green.** Six
  build jobs at 215/215. The sanitize job ran with halt-on-error UBSan:
  215/215 tests, then "expecting 16 examples … all 16 examples exited 0
  with no sanitizer reports".
- No second-round portability findings: all compilers agree on every test,
  including the move-order regression pins.
